# 代码导读 —— 逐文件讲解 + 面试问答

> 用途：面试前通读，确保每个文件都能讲清"是什么、为什么这么写"。
> 阅读顺序建议：先看「全景链路」，再按文件顺序读，最后看「高频问答」。

---

## 一、全景：两条链路

### 链路 A：上传文档（建知识库）

```
浏览器选文件
   → POST /api/documents/upload（multipart）
   → FastAPI 读取字节 → 解析 txt/md/pdf 为纯文本
   → split_text 切成 500 字符分块（相邻重叠 50）
   → 一个事务内：INSERT documents（1 条）+ INSERT chunks（N 条）
   → COMMIT，返回 document_id 和分块数
```

### 链路 B：提问（RAG 问答）

```
浏览器输入问题
   → POST /api/chat {conversation_id, question}
   → 校验会话存在
   → retrieve(question)：jieba 分词 → BM25 打分 → Top-K 分块
   → 分块拼进提示词（system 定规则 + user 放资料和问题）
   → 调大模型 API 生成回答
   → 一个事务内：插入 user 消息 + assistant 消息，更新会话时间
   → 返回 answer + sources
```

**一句话概括项目本质**：RAG = 检索（Retrieval）+ 生成（Generation），先查资料再让模型照着答，避免凭空编造。

## 二、逐文件讲解

### 1. `backend/main.py` —— 应用入口

```python
app = FastAPI(title="AI 知识库问答助手", version="1.0.0")
app.add_middleware(CORSMiddleware, allow_origins=["http://localhost:5173", ...])
app.include_router(documents.router)
app.include_router(chat.router)

@app.get("/api/health")
def health(): return {"status": "ok", ...}
```

三个要点：
- **创建应用**：`FastAPI()` 实例就是整个后端服务，自动生成 `/docs` Swagger 文档。
- **CORS 中间件**：前端跑在 5173、后端在 8000，端口不同=跨域。浏览器默认禁止跨域请求，必须由后端声明"允许 5173 来访问"。虽然开发时 Vite 代理已经绕过了跨域，但保留 CORS 是为了直接访问后端时也不报错。
- **health 接口**：部署和联调时用来验证"服务活着"，是最便宜的自检手段。

> 面试说法：FastAPI 基于 Starlette（ASGI）和 Pydantic，天然支持异步和自动参数校验；`include_router` 按业务域拆分路由，避免 main.py 越写越大。

### 2. `backend/config.py` —— 配置管理

```python
load_dotenv(...)                       # 读取项目根目录 .env
DB_PASSWORD = os.getenv("DB_PASSWORD", "")
LLM_API_KEY = os.getenv("LLM_API_KEY", "")
TOP_K = int(os.getenv("TOP_K", "3"))
```

- 所有敏感信息（数据库密码、API Key）和可调参数（分块大小、Top-K、温度）都从 `.env` 读，代码里不写死。
- `.env` 已写进 `.gitignore`，**上传 GitHub 不会泄露密钥**。
- 每个配置都有默认值，缺一项也能启动（除了 API Key 会给出明确报错）。

> 面试说法：这是 12-Factor App 的"配置与代码分离"原则；换环境（本地/服务器）只改环境变量，不改代码。

### 3. `backend/db.py` —— 数据库封装

```python
def get_conn():
    return pymysql.connect(..., cursorclass=DictCursor, autocommit=False)

def query(sql, args=None, one=False):    # SELECT
def execute(sql, args=None):             # INSERT/UPDATE/DELETE，带 commit/rollback
```

四个要点：
- **DictCursor**：查询结果返回字典，业务代码按列名取值，不用记住字段顺序。
- **参数化查询**：所有 SQL 用 `%s` 占位符 + 参数元组，**绝不拼接字符串** → 防 SQL 注入。
- **autocommit=False**：默认不自动提交，由业务代码决定 `commit` 还是 `rollback`，这样才能把多条语句放进同一个事务。
- **每次连接独立、用完关闭**：实现简单，适合中小项目；高并发场景应换成连接池（如 SQLAlchemy pool / DBUtils）。

> 面试追问"为什么不用 ORM"：这里刻意用原生 SQL，是为了展示表设计、关联查询、事务控制这些基本功；ORM 会更省事，但会把 SQL 细节藏起来。

### 4. `backend/text_splitter.py` —— 文本分块

```python
paragraphs = re.split(r"\n\s*\n|\n", text)
while len(para) > chunk_size:        # 超长段硬切
    chunks.append(para[:chunk_size])
    para = para[chunk_size - overlap:]   # 保留 overlap 衔接
if len(cur) + len(para) + 1 <= chunk_size: cur = f"{cur}\n{para}"  # 短段合并
```

- **为什么要分块**：模型上下文有限；检索单元越小越准；500 字符是一个中文段落的合理粒度。
- **overlap 的作用**：防止关键句子正好被切在边界上，前后各带 50 字符冗余。
- **两段逻辑**：正常段落合并到块；单段超长则硬切并按 overlap 接续。

> 面试说法：分块大小是效果调参的关键——太小语义不完整，太大检索粒度粗、浪费 token。这个参数（`CHUNK_SIZE`）在 `.env` 里可调。

### 5. `backend/retriever.py` —— BM25 检索器（项目技术核心）

三个函数：
- `_tokenize`：jieba 分词 + 转小写 + 去空白。
- `_bm25_score`：单个查询与单个分块的得分。
- `retrieve`：算 IDF、全量打分、排序、取 Top-K。

**BM25 公式逐项拆解**：

```
score += IDF × ( tf × (k1+1) ) / ( tf + k1 × (1 - b + b × doc_len/avg_dl) )
```

| 项 | 含义 | 作用 |
| --- | --- | --- |
| IDF | `log(1 + (N - df + 0.5)/(df + 0.5))` | 越罕见的词权重越高（"事务"比"的"重要） |
| tf | 该词在分块中的出现次数 | 出现越多分越高 |
| k1=1.5 | 词频饱和参数 | 防止 tf 无限加分（出现 10 次不等于重要 10 倍） |
| b=0.75 | 长度归一化 | 长文档天然容易命中，按长度惩罚，保证公平 |
| avg_dl | 全部分块的平均长度 | 归一化基准 |

**IDF 的直觉**：100 个分块里只有 3 个含"事务"→ 区分度极高；90 个都含"数据"→ 区分度低。

> 面试说法：BM25 是 TF-IDF 的改进版，解决了"长文档占便宜"和"词频无上限"两个问题；复杂度 O(分块数 × 查询词数)，当前全表扫描，数据量大时应换倒排索引或向量检索。

### 6. `backend/llm_client.py` —— 大模型客户端

```python
_client = OpenAI(base_url=LLM_BASE_URL, api_key=LLM_API_KEY)   # 单例
resp = _client.chat.completions.create(model=..., messages=..., temperature=...)
return resp.choices[0].message.content.strip()
```

- **OpenAI 兼容协议**：DeepSeek / Kimi / 通义千问 / 智谱都兼容这套接口，只改 `.env` 三行就能换模型，业务代码零改动。
- **全局单例**：客户端复用连接，避免每次请求重建。
- **temperature=0.3**：问答应偏保守准确，不要发散创作。

### 7. `backend/routers/documents.py` —— 文档接口

四个部分：
1. `_extract_text`：按扩展名分发——txt/md 直接 UTF-8 解码；pdf 用 pypdf 逐页提取。
2. `upload`：读字节 → 解析 → 分块 → 存原文件（uuid 重命名防覆盖）→ **事务写两张表**。
3. `list_documents`：`LEFT JOIN chunks + GROUP BY + COUNT` 一次查出"每个文档有几个分块"。
4. `delete_document`：查文件名 → 删库（分块靠外键 `ON DELETE CASCADE` 级联）→ 清理本地文件。

**事务为什么重要**：如果先插 documents 成功、插第 3 个 chunk 失败，没事务就会留下"文档存在但分块不全"的脏数据，检索时永远查不到完整内容。`try/commit` + `except/rollback` 保证要么全成、要么全不成。

**SQL 知识点**（面试可主动讲）：
- `LEFT JOIN`：以 documents 为主表，没分块的文档也显示（chunk_count=0）。
- `GROUP BY d.id` + `COUNT(c.id)`：分组聚合统计。
- `ON DELETE CASCADE`：删父表记录自动删子表，避免孤儿数据。
- 索引：`chunks.document_id` 建了索引，加速按文档查分块。

### 8. `backend/routers/chat.py` —— RAG 核心

```python
class ChatRequest(BaseModel):          # Pydantic 自动校验：类型不对直接 422
    conversation_id: int
    question: str

sources = retrieve(question, TOP_K)                     # 1 检索
context = "\n\n".join(f"【片段{i+1}】\n{s['content']}" ...)  # 2 拼上下文
messages = [{"role":"system",...}, {"role":"user", content=f"资料片段：\n{context}\n\n用户问题：{question}"}]
answer = chat(messages)                                 # 3 生成
# 4 同一事务插入 user + assistant 两条消息，更新会话 updated_at
```

四个设计点：
- **提示词分层**：system 定行为规则（只依据资料、资料不足要说明），user 放资料 + 问题。规则和内容分开，模型更听话。
- **检索为空时的兜底**：明确告诉模型"没找到资料，请如实告知"，而不是让它硬编。
- **异常转 502**：模型调用失败返回"调用大模型失败：原因"，前端能直接展示，排查成本低。
- **双写事务**：用户问题和回答要么都存、要么都不存，保证对话历史成对出现。

> 面试说法：RAG 缓解幻觉的原理=把"闭卷考试"变成"开卷考试"；本项目还返回 sources，前端可展示引用来源，提高可信度。

### 9. 前端 `frontend/src/`

- **`api.js`**：axios 实例，`baseURL: "/api"`，文档接口用 `FormData` 传 multipart；三个模块（documentApi / chatApi）按业务分组。
- **`vite.config.js`**：开发代理，`/api` 转发到 `http://127.0.0.1:8000`，前端代码只写相对路径，避免跨域、方便部署时统一改。
- **`App.vue`**：单文件组件（`<template>` + `<script setup>` + `<style>`）。
  - `ref` 定义响应式状态（会话、消息、文档、loading）。
  - `onMounted` 并发拉取会话和文档列表（`Promise.all`）。
  - `send()`：先本地 push 用户消息（立即显示）→ 调接口 → 追加回答 → 刷新会话列表。
  - `scrollBottom()`：`nextTick` 等 DOM 更新后再滚到底部。
  - 错误处理：`e.response?.data?.detail` 取后端的中文错误信息，直接弹给用户。

### 10. `tests/`

- `test_retriever.py`：纯函数单测——分词能切出关键词；相关分块得分必须高于无关分块。**不依赖数据库**，跑得快。
- `test_main.py`：接口冒烟——health 返回 ok；不带文件上传返回 422（验证 Pydantic/FastAPI 校验生效）。

> 面试说法：测试分层——算法逻辑用纯单测，接口用 TestClient 冒烟，数据库相关用人工联调。第一版不追求覆盖率，先保证核心链路不回归。

## 三、面试高频问答（背这 12 条）

1. **这个项目是做什么的？**
   私有知识库问答：上传文档自动分块入库，提问时检索最相关片段交给大模型回答，避免模型瞎编。

2. **RAG 是什么？为什么要 RAG？**
   检索增强生成。模型知识有截止时间、会幻觉、不知道你的私有资料；RAG 先查资料再回答，答案有依据、可更新、成本低（不用微调）。

3. **为什么要分块？块多大合适？**
   上下文有限 + 检索要"小而准"。本项目 500 字符、重叠 50，参数可配；太小语义不完整，太大检索粗、浪费 token。

4. **BM25 原理？和 TF-IDF 区别？**
   IDF 加权 + 词频饱和（k1）+ 长度归一化（b）。比 TF-IDF 多了饱和和归一化，避免长文档和词频堆砌占便宜。

5. **检索为什么要分词？**
   中文没有空格，jieba 切词后才能按词统计；不分词只能按字匹配，相关性差。

6. **事务用在哪？为什么？**
   上传文档（documents + chunks）和保存问答（user + assistant 两条消息）。保证多表写入原子性，避免半截数据。

7. **SQL 注入怎么防？**
   全部参数化查询（%s 占位），不拼字符串；数据库把参数当数据而非 SQL 执行。

8. **索引建在哪？为什么？**
   `chunks.document_id`（按文档查分块）、`messages.conversation_id`（查会话历史）、`created_at/updated_at`（排序）。高频过滤/排序的列才建，索引多了会拖慢写入。

9. **怎么换大模型？**
   OpenAI 兼容协议，改 `.env` 的 base_url / api_key / model 三行即可，代码不用动。

10. **检索为空怎么办？**
    提示词明确要求"如实告知并建议补充资料"，不硬编；前端可展示 sources 让用户判断可信度。

11. **怎么调试接口的？**
    Swagger `/docs` 直接调；curl 测 multipart；后端日志看异常；前端用 `detail` 字段展示错误。

12. **项目有哪些不足/怎么优化？**
    检索是全表扫描（应上倒排索引/向量库）；单机单库（应连接池+缓存）；无用户体系；无流式输出；可加 Rerank 和引用高亮。
